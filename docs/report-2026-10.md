# Do AI dev tools do what their docs say? 80 repos, checked line by line

*October 2026 · Emanuele Cella · checked with [Elliot](../README.md)*

**23 of 80 popular open-source AI developer tools (29%) have at least one promise in their docs that the code doesn't keep.** Most of them are about the things users care about most: telemetry, permissions, sandboxes and secrets.

## What we checked

- **80 repositories:** MCP servers, coding-agent tools, Claude Code / Cursor / Codex add-ons. Mostly 400 to 15,000 GitHub stars, all with commits in the last 3 months. They're maintained both by independent developers and by small companies.
- **711 claims taken from their READMEs and docs:** "no telemetry", "read-only", "binds to localhost", "secrets are encrypted", "supports X", "defaults to Y".
- **How each claim was checked:**
  - Elliot traced each claim into the code at the latest commit.
  - It rejected any citation it couldn't find at the quoted file and line, and re-ran every "this doesn't exist" search itself.
  - A second agent, which hadn't seen the audit, tried to refute every finding.
  - Then I re-read every medium and high finding by hand.

## Results

| | Claims | Share |
|---|---|---|
| Hold up in the code | 636 | 89% |
| Partly true (a gap that misleads users) | 33 | 5% |
| False | 23 | 3% |
| Can't be checked from the code (depends on a deployment or service) | 19 | 3% |

**Hand check:** of the 36 medium and high findings, none turned out wrong. One was arguable, and 4 were true but too minor to report.

## What breaks most often

| Kind of promise | Repos with a broken one | Typical pattern |
|---|---|---|
| Security controls (permissions, sandboxes, network binding, secrets at rest) | 9 | A safety default documented one way and implemented the other; a "blocked" path that is blocked on one entry point and open on another |
| Telemetry and privacy | 6 | "No paths or personal data", while raw error messages or stack traces, which contain paths and usernames, are sent anyway |
| Features and options that drifted | 8 | A flag kept in the docs after the code stopped honouring it; a supported platform listed in a table but missing from the installer |

Three patterns came up again and again:

1. **The docs describe the plan, the code is what shipped.** A feature gets a second implementation (a new provider, a new storage mode) and the old sentence stays.
2. **A guard on one door, not the others.** A safety check added to the CLI flag but not to the config file or the TUI shortcut that leads to the same mode.
3. **"Anonymized" means "truncated".** Error reporting that cuts messages to 200 characters, but doesn't remove the paths in them.

None of this looks deliberate. These are fast-moving projects, many of them written with coding agents, where nobody re-reads the README after each merge.

## What we're doing with the findings

- **Security issues:** reported privately to the maintainers. They're not named here.
- **Docs mismatches:** opened as normal issues, one at a time, with the exact lines and a suggested fix.
- **Projects named only after their issue is public:** for example dyad, whose triage bot confirmed a sandbox documented as read-only that can write files ([#4879](https://github.com/dyad-sh/dyad/issues/4879)).
